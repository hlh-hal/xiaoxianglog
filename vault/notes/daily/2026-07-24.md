# 2026-07-24 网页白屏与前端发布链路修复

## 事故

- 官网 `https://www.xiaoxianglog.cn/` 白屏，浏览器在 `/assets/index-B_vqF2v_.js:2898` 报 `Invalid or unexpected token`。
- 线上主包只有 `2,354,070` 字节，文件结尾停在半截字符串 `className:"...text-on-s`，确认是 FTP 上传截断，不是用户数据丢失、接口异常或浏览器兼容问题。
- Android 正常是因为 APK 使用内置前端资源；它不能证明官网静态资源完整。

## 根因

- 旧 `deploy-upload.ps1 -Target front` 按目录枚举顺序先上传 `index.html`，再上传主 JS。
- FTP 请求返回成功后没有检查远端实际大小，也没有从公网反向下载校验。入口因此可能先指向一份尚未上传完成或已经截断的资源。
- `index.html` / `sw.js` 直接覆盖，入口文件自身也存在上传到一半即对外可见的风险。

## 修复

- 所有 FTP 上传完成后强制执行远端 `SIZE`，字节数不一致即进入重试；后端和其他上传目标也自动受益。
- 前端改为两阶段发布：先上传除 `index.html` / `sw.js` 外的 payload；任一失败都不激活新入口。
- 激活前从公网反向下载 `dist/index.html` 引用的主 JS/CSS，校验字节数与 SHA256；JS 额外执行 `node --check`。
- `index.html` / `sw.js` 先上传到随机临时名，再把旧文件改名为 rollback 备份、将已验证临时文件改名就位；失败时自动恢复旧文件。
- 服务器 FTP 不允许 RNTO 直接覆盖已有文件，会返回 553；因此不能省略“旧文件先改名为备份”的兼容步骤。
- 新增 `front-activate` 目标，只允许在重新通过公网资源校验后重试入口激活，供 payload 已完整上传但激活失败时恢复使用。

## 发布与验证

- `npm run lint`：通过。
- `npm run build`：通过；主包 `assets/index-BFHyofyt.js`，大小 `2,368,928` 字节，SHA256 `7A39CB21445089EAB397025913378C5B5754CE37A77E1DED699C829B2A934D24`。
- 首轮新流程：41 个 payload 文件全部通过 FTP SIZE；主 JS/CSS 通过公网 SHA256 与语法检查；直接覆盖式 RNTO 被 553 拒绝，门禁正确停止且没有继续破坏入口。
- 兼容 FTP 语义后执行 `deploy-upload.ps1 -Target front-activate`：入口与 Service Worker 原子切换成功，公网首页引用新主包。
- 使用全新无缓存 Edge/Puppeteer 打开官网：HTTP 200、标题“小象日志”、React 根节点已挂载、页面正文正常、控制台与 page error 均为 0。

## 后续规则

- 发布成功的定义不是“上传命令退出 0”，而是“远端大小一致 + 公网哈希一致 + JS 可解析 + 页面真实挂载”。
- 内容哈希资源必须先于入口发布；入口只能引用已经在公网验证通过的资源。
- 任何修改前端发布脚本的任务，都必须至少覆盖一次失败不切入口路径和一次真实浏览器验收。
