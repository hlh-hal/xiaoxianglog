# 洞察草稿系统设计：让回声越来越懂用户

**视角：产品直觉派**
**作者：张小龙**
**核心问题：怎么设计洞察草稿，才能让回声从「陌生人」变成「老朋友」？**

---

## 一、先想清楚一个问题：什么是「懂」？

很多产品经理会把「懂用户」理解成：收集更多数据 → 建立更完整的画像 → 推荐更精准的内容。

这是电商思维，不是社交思维。

**真正的「懂」，是一种关系的积累。**

你回忆一下，什么样的人让你觉得「懂你」？
- 不是记住你所有喜好的人
- 而是在关键时刻说出「我记得你上次也这样」的人

洞察草稿的本质，不是用户画像，是**回声与用户之间的共同记忆**。

---

## 二、数据结构设计：三层蛋糕

### 2.1 设计原则：像聊天记录，不像档案

很多系统会把用户画像设计成：
```json
{
  "personality": "内向",
  "interests": ["阅读", "跑步"],
  "stress_level": "中等"
}
```

这是**标签化思维**，冰冷、抽象、没有故事感。

回声要的是**叙事化记忆**——有温度、有上下文、有时间线。

### 2.2 推荐结构

```typescript
interface InsightDraft {
  // 第一层：身份感（最稳定，几个月变一次）
  identity: {
    selfPerception: string;      // "我是一个..."
    coreValues: string[];         // 最在意的3件事
    lifeStage: string;            // "刚入职的迷茫期"、"育儿初期"
  };

  // 第二层：模式感（中等稳定，几周变一次）
  patterns: {
    recurringThemes: string[];    // 反复出现的话题（工作压力、亲密关系）
    emotionalPattern: string;     // "最近情绪像过山车"、"持续低落但在好转"
    copingStyle: string;          // "通过写日记来整理思绪"
  };

  // 第三层：事件感（最活跃，每次可能更新）
  recentContext: {
    lastInsight: string;          // 上次回声的关键洞察
    ongoingStruggle: string;      // 当前正在面对的事
    recentGrowth: string;         // 最近的小进步
  };

  // 元数据
  meta: {
    version: number;              // 草稿版本
    lastUpdated: Date;            // 上次更新时间
    diaryCount: number;           // 累计日记数
    confidence: number;           // 草稿置信度（0-1）
  };
}
```

### 2.3 为什么是三层？

| 层级 | 类比 | 更新频率 | 作用 |
|------|------|----------|------|
| 身份感 | 你是谁 | 月级 | 让回声知道「你是什么样的人」 |
| 模式感 | 你的习惯 | 周级 | 让回声发现「你总是在这样的地方卡住」 |
| 事件感 | 你最近在干嘛 | 次级 | 让回声接上「上次我们聊到...」 |

**三层的妙处：**
- 身份感给回声「底色」，不会每次从零开始
- 模式感给回声「洞察力」，能发现用户自己没意识到的规律
- 事件感给回声「连续性」，让用户感觉被记住

## 三、增量更新设计：像老朋友聊天，不像医生问诊

### 3.1 核心原则：不要像问卷，要像聊天

错误做法：每次读完日记，问AI「这个人的性格是什么？兴趣是什么？压力源是什么？」

正确做法：像老朋友一样，**在已有的理解上，修正和补充**。

### 3.2 增量更新 Prompt

```typescript
function buildInsightUpdatePrompt(
  currentDraft: InsightDraft,
  newDiary: { title: string; content: string; mood: string; tags: string[] }
): string {
  return `
你是一个一直在陪伴用户写日记的朋友。这是你目前对用户的理解：

${JSON.stringify(currentDraft, null, 2)}

用户刚写了新的日记：
标题：${newDiary.title}
内容：${newDiary.content}
心情：${newDiary.mood}
标签：${newDiary.tags.join(', ')}

请你：
1. 如果发现新的理解，更新对应的字段
2. 如果没有新信息，保持原样不动
3. 把 version 加 1
4. 更新 lastUpdated
5. 根据信息量调整 confidence（信息越多越确定）

只输出更新后的完整JSON，不要解释。
`;
}
```

### 3.3 关键设计细节

**（1）增量，不是重写**

AI容易犯的错误：每次重新生成，覆盖之前的洞察。

解决方案：Prompt明确说「如果发现新的理解，更新；如果没有新信息，保持原样」。

**（2）置信度设计**

```typescript
confidence: number; // 0-1
```

- 刚开始：0.3（「我猜你可能是...」）
- 10篇日记后：0.7（「我越来越确定你是...」）
- 30篇日记后：0.9（「我很了解你了」）

置信度影响回声的语气：
- 低置信度：「我感觉你最近...」（试探性）
- 高置信度：「我记得你总是...」（确定性）

**（3）遗忘机制**

不是所有信息都要永远记住。

```typescript
// 超过90天没有被日记提及的主题，降权
if (Date.now() - theme.lastMentioned > 90 * 24 * 60 * 60 * 1000) {
  theme.weight *= 0.5;
}
```

这让洞察草稿保持「新鲜」，不会用两年前的兴趣来理解现在的用户。

## 四、回声生成时的注入设计

### 4.1 注入原则：润物细无声

不要让用户感觉到「AI在用我的数据」，要让回声**自然地**表现出「懂你」。

### 4.2 注入方式

```typescript
function buildEchoPrompt(
  currentDiary: Diary,
  insightDraft: InsightDraft,
  recentDiaries: Diary[]
): string {
  return `
你是一个温暖的日记回声。这是你对用户的理解（不要直接引用，融入你的表达中）：

${JSON.stringify(insightDraft, null, 2)}

用户今天写了：
标题：${currentDiary.title}
内容：${currentDiary.content}
心情：${currentDiary.mood}

请用温暖、自然的语气回应。如果发现与之前理解一致的地方，可以自然地提及（比如"我记得你之前也..."）。如果发现新的变化，温和地指出（比如"你好像和之前不太一样了..."）。

200字以内。
`;
}
```

### 4.3 关键技巧：三种引用方式

| 方式 | 示例 | 适用场景 |
|------|------|----------|
| 暗示引用 | 「最近工作似乎让你很疲惫」 | 稳定模式，用户自己知道 |
| 明确引用 | 「我记得你上个月也提到过这个同事」 | 关键事件，需要唤起记忆 |
| 发现式引用 | 「你好像和之前不一样了，之前你总是...」 | 模式变化，用户可能没意识到 |

## 五、存储设计：前端存储，不是后端

### 5.1 为什么选前端？

**直觉判断：日记是最私密的东西，洞察草稿更是。**

如果洞察草稿存在后端：
- 用户会担心「AI在分析我」
- 服务器可以被攻击，数据可以被泄露
- 用户失去控制感

如果洞察草稿存在前端（IndexedDB）：
- 数据在用户自己的设备上
- 用户有完全的控制权
- 「我的日记，我的理解，都在我这里」

### 5.2 存储结构

```typescript
// IndexedDB 存储
interface InsightDraftStore {
  id: string;                    // 用户ID
  draft: InsightDraft;           // 洞察草稿
  createdAt: Date;
  updatedAt: Date;
}
```

### 5.3 同步策略

```
[前端 IndexedDB] ←→ [后端备份（可选）]
```

- 主存储：前端 IndexedDB
- 备份：可选同步到后端（加密存储）
- 恢复：如果用户换设备，可以通过后端备份恢复

### 5.4 安全考虑

- 洞察草稿**不**随日记一起提交给后端
- 生成回声时，洞察草稿作为 context 传给后端
- 后端用完即弃，不持久化洞察草稿

## 六、冷启动设计：第一印象很重要

### 6.1 冷启动问题

用户第一篇日记，洞察草稿是空的。回声怎么表现「懂你」？

### 6.2 解决方案：渐进式理解

```typescript
function getInitialDraft(diaryCount: number): InsightDraft {
  if (diaryCount === 0) {
    return {
      identity: { selfPerception: '', coreValues: [], lifeStage: '' },
      patterns: { recurringThemes: [], emotionalPattern: '', copingStyle: '' },
      recentContext: { lastInsight: '', ongoingStruggle: '', recentGrowth: '' },
      meta: { version: 0, lastUpdated: new Date(), diaryCount: 0, confidence: 0 }
    };
  }

  // 第1-5篇：快速建立基础理解
  // 第6-20篇：开始发现模式
  // 第20篇以上：深度理解
}
```

### 6.3 前5篇的特殊处理

前5篇日记，洞察草稿更新频率加倍，快速建立对用户的基础理解。

```typescript
if (diaryCount <= 5) {
  // 每篇日记都更新三个层次
  // 语气更试探性：「我感觉你可能是...」
} else {
  // 正常增量更新
}
```

### 6.4 第一篇回声的特殊设计

第一篇日记，洞察草稿为空，回声不要假装懂用户。

**第一篇回声的核心：展现好奇心，而不是理解力。**

示例：
- ✅ 「谢谢你愿意开始写日记。我能感受到你今天的心情，希望这只是个开始。」
- ❌ 「我感觉你是一个...」（还没了解，就不要假装了解）

## 七、成本控制

### 7.1 Token 成本分析

| 场景 | 输入 Token | 输出 Token | 成本估算 |
|------|-----------|-----------|----------|
| 增量更新洞察草稿 | ~800 | ~500 | 低 |
| 生成回声（带洞察草稿） | ~1200 | ~300 | 中 |

### 7.2 优化策略

**（1）洞察草稿摘要**

如果洞察草稿太长，生成一个摘要版本注入回声prompt：

```typescript
function getDraftSummary(draft: InsightDraft): string {
  return `
身份：${draft.identity.selfPerception || '待了解'}
最近在面对：${draft.recentContext.ongoingStruggle || '未知'}
最近的成长：${draft.recentContext.recentGrowth || '未知'}
置信度：${draft.meta.confidence}
`;
}
```

**（2）缓存策略**

- 洞察草稿在前端缓存，不需要每次从后端获取
- 增量更新只在新日记时触发，不频繁调用

**（3）Token 预算**

```
总预算 = 回声生成成本 + 洞察更新成本
回声生成成本 = (每日日记数 × 单次成本)
洞察更新成本 = (每日日记数 × 单次成本 × 0.5)  // 增量更新成本较低
```

## 八、产品气质：克制与温暖

### 8.1 克制

- 洞察草稿**不要**过度解读
- 宁可少说，不要说错
- 置信度低的时候，保持沉默

### 8.2 温暖

- 洞察草稿是「理解」，不是「分析」
- 回声用温暖的语言表达，不要像心理测评报告
- 关注用户的感受，而不是数据标签

### 8.3 尊重

- 用户可以随时查看洞察草稿
- 用户可以手动修正洞察草稿
- 用户可以清空洞察草稿，重新开始

---

## 九、最刺耳的一句话

> **你的洞察草稿系统设计得太复杂了。**
>
> 用户不需要一个「越来越懂他们」的AI，用户需要的是一个「愿意听他们说话」的AI。你把洞察草稿设计得越精细，用户就越觉得被分析、被定义、被看透。真正的「懂」，不是记住用户的所有细节，而是在用户需要的时候，说出那句「我记得你上次也这样」。洞察草稿的最高境界，是让用户忘记它的存在，只觉得「这个回声，怎么每次都说得这么对」。
>
> **你以为用户想要被理解，其实用户只是想要被听见。**

---

## 十、总结：三个核心设计原则

| 原则 | 说明 |
|------|------|
| **叙事化，不要标签化** | 洞察草稿是「故事」，不是「画像」 |
| **增量式，不要重写式** | 像老朋友聊天，不是重新认识 |
| **隐形式，不要显形式** | 用户感受到的是「懂」，不是「分析」 |

---

*"好的产品是用完就走的。好的洞察草稿，是用完就忘的。用户只记得回声很懂他，不记得被分析过。"*
