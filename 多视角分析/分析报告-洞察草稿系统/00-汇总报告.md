# 洞察草稿系统设计 — 多视角诊断报告

> 分析日期：2026-06-07
> 视角：Dan Sullivan、马斯克、张小龙、MrBeast、芒格、蒂尔、乔布斯、贝佐斯、张一鸣、任正非
> 分析对象：DailyEcho的洞察草稿从"死系统"到"活系统"的具体设计

---

## 多人共识

### 1. 存储在前端 IndexedDB，隐私优先（10/10 一致）

日记是最私密的数据。洞察草稿和日记数据存在同一个生命周期里，不上传服务器。

> 蒂尔："前端IndexedDB存完整草稿——隐私+数据主权。"
> 张小龙："日记的隐私属性决定了本地优先。"

### 2. 洞察草稿应该有"版本"和"置信度"（8/10 一致）

不是所有洞察都一样可靠。需要区分"刚发现的模式"和"持续确认的特质"。

> 张一鸣："各维度设置不同衰减率——今日主线衰减快，人格特质几乎不衰减。"
> 芒格："没有置信度的洞察就是幻觉。"

### 3. 注入回声时应该是"潜台词"，不是"附加模块"（7/10 一致）

> 乔布斯："让草稿成为回声的灵魂。不是'参考一下洞察草稿'，而是'带着对你的理解，说出此刻该说的话'。"
> 张小龙："叙事化不要标签化，隐形式不要显形式。"

### 4. 冷启动：第一天不能是空白（6/10 一致）

> MrBeast："Wow Moment在前5篇——必须'准但明显不完整'，激发好奇心。"
> 乔布斯："第一天的体验决定了用户是否回来。"

### 5. 先验证留存影响，再做复杂系统（5/10 指出）

> 马斯克："先用最蠢方案验证'回声记忆对留存是否有因果影响'，再优化。"
> 任正非："如果留存率本身很低，做洞察持久化是给尸体穿漂亮衣服。"

## 有意思的分歧：数据结构该多复杂？

| 立场 | 代表 | 设计 |
|------|------|------|
| **极简派** | 乔布斯 | 1个字段：`sentence`（一句话洞察）|
| **均衡派** | Dan Sullivan、张小龙、贝佐斯 | 4-5个维度，每维度一段叙述性文字 |
| **完整派** | 张一鸣 | 完整向量结构，含置信度/衰减率/证据链/趋势 |

**分析**：极简派的"一句话"在Day 1就能见效，但随时间增长信息密度会溢出。完整派结构化程度高但冷启动困难。**建议**：从均衡派起步（4个维度各1-2句），随用户数据增长再考虑是否引入衰减和置信度。

## 具体设计方案（综合10个视角共识）

### 数据结构

```typescript
interface InsightDraft {
  userId: string;
  version: number;           // 版本号，每次更新+1
  updatedAt: string;         // ISO时间戳
  
  // 层1：近期关注（每3-5天可能变化）
  recentFocus: string;       // 1-2句，用户最近在关注什么
  
  // 层2：反复出现的模式（变化较慢）
  recurringPatterns: string[]; // 2-3条，用户反复出现的行为/情绪模式
  
  // 层3：稳定的自我认知（几乎不变，除非日记证据充分推翻）
  coreTraits: string[];      // 2-3条，用户展现出的稳定特质
  
  // 层4：成长信号（新增的、正在萌芽的变化）
  growthSignals: string[];   // 1-2条，最近出现的积极变化
}
```

**总控80-150字。** 不是档案，是朋友对你的印象。

### 增量更新 Prompt

```
你是一个记忆编辑，负责维护用户的"自我认知笔记"。

今天的日记：
{新日记内容}

当前笔记：
{当前草稿JSON}

任务：
1. 如果今天的日记有新信息，更新相关字段
2. 如果今天的信息和已有笔记矛盾，更新并说明原因
3. 如果今天没有新信息，保持不变
4. 每个字段用1-2句自然语言，不要术语和标签
5. 语气：像朋友对你的印象描述，不是心理报告

输出更新后的完整笔记（JSON格式）。
```

温度0.3保证一致性，每天最多1次调用。

### 回声注入方式

```
你对这个人的了解：
{草稿的自然语言版本，不暴露JSON结构}

ta今天又写了一篇日记。

用你对ta的了解，回应ta今天的日记。
不要提你知道的信息。让它自然流露。
像老朋友——不"我记得你上次说……"，而是带着理解说出此刻该说的话。
```

### 存储：IndexedDB

在 `diaryService.ts` 中新增 `insightDraft` store：
- 存储完整草稿JSON
- 与日记数据同一生命周期
- 不上传后端（当前阶段）

### 冷启动策略

| 阶段 | 日记数 | 策略 |
|------|--------|------|
| 第1篇 | 0→1 | 不生成草稿，回声用通用温暖模板 |
| 第2-5篇 | 1→5 | 生成初始草稿，字段简短，标注"初步印象" |
| 第5篇+ | 5+ | 正常增量更新 |

### 成本控制

- 每次增量更新：~800-1200 tokens（约¥0.01）
- 回声生成时注入草稿：~200额外tokens（可忽略）
- 每天最多1次更新调用
- 日记内容无实质性变化时跳过更新

## 实施优先级（任正非的三阶段框架）

### Phase 1：最小闭环（1-2周）

**只做三件事：**
1. IndexedDB新增insightDraft存储
2. 回声生成时读取草稿注入prompt
3. 回声生成后用同一个response更新草稿（不额外调用）

**不做：** 独立的更新调用、衰减机制、用户可见页面

### Phase 2：增量更新（第3-4周）

4. 独立的增量更新prompt和API调用
5. 冷启动策略实现
6. 版本号和基础置信度

### Phase 3：体验深化（第5-8周）

7. 跨时间模式检测（"你这周第三次提到XX"）
8. 用户可见的"系统对我的理解"页面
9. 衰减和遗忘机制
