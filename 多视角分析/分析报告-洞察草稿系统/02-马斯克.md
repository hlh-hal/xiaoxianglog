# 马斯克视角：洞察草稿系统设计

> 用第一性原理拆解。不要问"别人的日记系统怎么做"，要问"人为什么写日记"以及"AI回声到底在解决什么物理问题"。

---

## 0. 第一性原理：回到物理学

### 日记产品的本质方程

```
用户价值 = f(被理解的感觉, 看见自己的成长)
```

写日记的人，核心需求不是"记录事件"——手机相册、备忘录都能做。他们要的是：**有人看见我**。

AI回声的本质工作：**把用户自己都没注意到的模式，温柔地反射回去**。

"你这周提了三次'累'，但每次都在深夜写完日记——你其实比你以为的更有韧性。"

这种回声只有在系统**记住用户**时才可能产生。否则每次回声都是陌生人寒暄。

### 洞察草稿的本质定义

洞察草稿 = **用户画像的压缩增量快照**

不是全量日记的副本（太贵、太慢），而是每次从新日记中提取**值得记住的信号**，更新到一个持续演化的理解模型中。

类比：火箭回收系统不会保留每次发射的完整遥测数据，而是提取关键参数（燃料效率、热防护损耗、姿态偏差）形成持续改进的模型。

## 1. 洞察草稿该包含什么？

### 信息设计的两条原则

**原则1：只存AI下次回声真正会用到的信息**
问自己：如果这些字段在下次生成回声时消失了，回声质量会下降吗？如果不会，删掉它。

**原则2：压缩比决定一切**
用户写了500字日记，洞察草稿的增量更新应该只有~200 token。记忆是廉价的，但上下文窗口不是。

### 数据结构

```typescript
interface InsightDraft {
  // ============ 身份层：TA是谁 ============
  identity: {
    // 人格特质标签（3-5个，从日记语料中提取）
    traits: string[];           // e.g. ["自我要求高","共情能力强","容易内耗"]
    // 核心价值观（1-2句，极简压缩）
    values: string;             // e.g. "在意公平，重视家人感受"
    // 表达风格（影响回声语气匹配）
    tone: string;               // e.g. "内敛，喜欢用比喻，偶尔自嘲"
  };

  // ============ 时间层：最近在发生什么 ============
  current: {
    // 最近一周的情绪走向（极简：一个词+一个趋势箭头）
    mood_trend: string;         // e.g. "疲惫↓" / "平静→" / "期待↑"
    // 当前核心矛盾/困扰（最多2个）
    active_tensions: string[];  // e.g. ["工作量大vs想陪家人","对自己的高标准vs现实差距"]
    // 今天日记的主线（一句话）
    today_mainline: string;     // e.g. "和领导谈了加薪，又紧张又期待"
    // 最近反复出现的主题词
    recurring_themes: string[]; // e.g. ["睡眠","加班","妈妈"]
  };

  // ============ 成长层：TA在往哪走 ============
  growth: {
    // 最近一次被观察到的成长瞬间
    last_growth_moment: string; // e.g. "6月5日主动和朋友说了不满，以前会忍"
    // 用户自己说想改变的事（原文摘录，不改写）
    stated_goals: string[];     // e.g. ["想早睡","不想那么在意别人的看法"]
    // AI观察到的未被用户自己发现的模式（核心价值所在）
    blind_spot_signals: string[]; // e.g. ["每次写完焦虑日记后第二天会写行动清单，行动力其实很强"]
  };

  // ============ 元数据 ============
  meta: {
    last_updated: string;       // ISO日期
    diary_count: number;        // 累计日记数
    draft_version: number;      // 草稿版本号（用于冲突检测）
  };
}
```

### 为什么是这些字段，不是别的？

| 字段 | 不存的后果 | 存了的价值 |
|------|-----------|-----------|
| identity.traits | 回声永远泛泛而谈 | "作为一个XX的人，你今天……" |
| current.mood_trend | 无法识别情绪变化 | "比上周好一些了" vs "连续三天疲惫" |
| current.active_tensions | 回声不提核心矛盾，用户觉得AI没听懂 | 直接回应用户最在意的事 |
| growth.last_growth_moment | 无法做成长反馈 | "还记得上次你……这次也是" |
| growth.blind_spot_signals | 这是回声最独特的价值来源 | 用户看不到的模式，AI看见了 |

**我不存的东西**：
- 具体事件细节（"今天吃了火锅"）→ 日记原文有，不需要重复
- 完整情绪曲线 → 太贵，压缩成趋势
- 正面/负面评分 → 过度简化，不如保留原始信号

## 2. 增量更新机制

### 核心设计：每次更新 = 一次轻量推理

```
输入：旧洞察草稿 + 今日新日记
输出：新洞察草稿
```

不是把所有历史日记重跑一遍（O(n)成本爆炸），而是**增量融合**——像数据库的WAL日志，每次只追加变更。

### 更新Prompt设计

```markdown
你是小象洞察引擎。你的工作是维护一个用户的"理解快照"。

## 输入
### 旧洞察草稿（JSON）：
{existing_draft_json}

### 今日新日记：
{new_diary_text}

## 任务
基于今日新日记，更新洞察草稿。规则：

1. **identity层**：只在新日记提供了强信号时才修改。
   - 如果用户反复表现出某个特质，加入traits（最多5个，去重）
   - 如果用户直接表达价值观，更新values
   - tone一般不改，除非用户风格明显变化

2. **current层**：每个字段都用今日信息刷新。
   - mood_trend：对比最近趋势，更新方向
   - active_tensions：今日日记涉及的矛盾加入，旧矛盾如果3天未提及移除
   - today_mainline：今日主线（新）
   - recurring_themes：统计最近7天，保留出现≥2次的主题

3. **growth层**：谨慎更新。
   - last_growth_moment：只在有明确成长行为时更新（不是"想改变"，是"做到了"）
   - stated_goals：用户明确提出的目标加入，不删旧的（除非用户说放弃）
   - blind_spot_signals：这是最高价值字段。只在发现用户未自知的模式时添加。
     例：用户总写焦虑日记但每次最后都有行动方案 → "行动力是你的隐藏优势"
     上限3条，过期的替换。

4. **输出格式**：只输出更新后的完整JSON，不解释。
```

### 更新策略的工程细节

```typescript
async function updateInsightDraft(
  existingDraft: InsightDraft,
  newDiaryText: string
): Promise<InsightDraft> {
  const prompt = UPDATE_PROMPT
    .replace('{existing_draft_json}', JSON.stringify(existingDraft, null, 2))
    .replace('{new_diary_text}', newDiaryText);

  const response = await callAI({
    model: 'mimo',
    messages: [{ role: 'user', content: prompt }],
    temperature: 0.3,  // 低温度：一致性 > 创造性
    max_tokens: 800,   // 硬上限，防止输出膨胀
  });

  const newDraft = JSON.parse(response);

  // 校验：确保字段没有丢失
  newDraft.meta.draft_version = existingDraft.meta.draft_version + 1;
  newDraft.meta.last_updated = new Date().toISOString();
  newDraft.meta.diary_count = existingDraft.meta.diary_count + 1;

  return newDraft;
}
```

### 成本控制

| 指标 | 值 | 说明 |
|------|-----|------|
| 单次更新token消耗 | ~600-1000 | 旧草稿(~300) + 新日记(~300-500) + 输出(~300) |
| 回声生成时注入token | ~300 | 草稿JSON序列化 |
| 每日额外AI调用 | 1次 | 更新草稿 |
| 每月额外成本（1000日活） | ~30000次调用 | MiMo模型成本可控 |

**关键约束**：max_tokens=800。草稿大小有上界，不会随日记数量无限膨胀。这是压缩的本质——有信息损失，但损失的是不重要的信息。

## 3. 回声生成时怎么注入？

### 三段式Context组装

```markdown
## 系统Prompt（固定）

你是一个温暖的日记回声助手。你的回应要让用户感到"被看见了"。

## Context注入（动态）

### 你对用户的了解（洞察草稿）：
{insight_draft_json}

### 今日日记：
{today_diary_text}

## 生成规则
1. 先回应今日日记的情绪和内容（这是基础）
2. 如果洞察草稿中有相关的active_tensions，温和地关联
3. 如果有growth信号（特别是last_growth_moment和blind_spot_signals），
   在合适的时候给一句成长反馈——但不要每次都提，用户会觉得被监视
4. 语气匹配identity.tone
5. 长度：100-200字，不要写信，像朋友回复消息
```

### 注入的克制原则

> "拥有记忆不意味着要炫耀记忆。"

回声里最糟糕的体验：AI突然说出你三个月前的细节，像被偷窥。

正确做法：
- **常用**：情绪趋势、当前矛盾、人格特质 → 每次回声都用
- **偶尔用**：成长瞬间、盲点信号 → 10次回声用2-3次，像惊喜
- **从不直接引用**：把洞察草稿转化成自然语言，不要说"根据我的记录，你……"

## 4. 存储位置

### 方案：SQLite后端存储 + IndexedDB缓存

```
[推荐架构]

后端 SQLite
├── insight_drafts 表
│   ├── user_id (主键关联)
│   ├── draft_json (TEXT, 完整JSON)
│   ├── version (INTEGER)
│   └── updated_at (DATETIME)
│
前端 IndexedDB (缓存层)
├── store: "insightCache"
│   ├── key: "currentDraft"
│   ├── value: InsightDraft JSON
│   └── synced_version: number
```

**为什么后端存而不是纯前端？**
- 用户换浏览器/设备 → 洞察不丢
- 后端可以做定时归档（旧版本快照）
- IndexedDB偶尔被清理（Safari隐身模式、存储压力）

**前端缓存的作用？**
- 避免每次回声都请求后端草稿
- 离线场景也能用（但更新需要在线）

### Prisma Schema

```prisma
model InsightDraft {
  id          Int      @id @default(autoincrement())
  userId      Int      @unique
  draftJson   String   @db.Text
  version     Int      @default(1)
  updatedAt   DateTime @updatedAt

  user        User     @relation(fields: [userId], references: [id])
}
```

## 5. 冷启动策略

### 第一篇日记：没有历史

```typescript
function createColdStartDraft(diaryText: string): InsightDraft {
  // 第一篇日记直接做一次全量分析，不做增量
  // Prompt专门针对"首次分析"场景
  return {
    identity: {
      traits: [],      // 不猜，留空
      values: "待观察",
      tone: "待观察"
    },
    current: {
      mood_trend: "初始",
      active_tensions: [],
      today_mainline: "",  // 由分析填充
      recurring_themes: []
    },
    growth: {
      last_growth_moment: "",
      stated_goals: [],
      blind_spot_signals: []
    },
    meta: {
      last_updated: new Date().toISOString(),
      diary_count: 1,
      draft_version: 1
    }
  };
}
```

### 1-5篇日记：逐步积累

- traits和tone需要2-3篇日记才能有可靠信号
- 盲点信号至少需要5篇才能识别模式
- **回声在这个阶段应该更轻量、更通用**，不要假装很了解用户

### 5篇以上：正常运行

- 所有字段开始有实质内容
- 回声可以开始做成长反馈和模式识别

### 30天未写日记：休眠处理

```typescript
// 如果最后更新距今>30天
if (daysSinceUpdate > 30) {
  // current层清空（不再适用）
  draft.current = {
    mood_trend: "久未更新",
    active_tensions: [],
    today_mainline: "",
    recurring_themes: []
  };
  // identity和growth保留（人格和历史成长不会消失）
}
```

## 6. 成本与风险控制

### Token预算上限

```
每次回声生成的总token预算：

系统Prompt:     ~200 token (固定)
洞察草稿注入:   ~300 token (上限)
今日日记:       ~500 token (用户输入)
AI回声输出:     ~300 token (控制长度)
─────────────────────────────
总计:          ~1300 token / 次

洞察草稿更新:
旧草稿输入:     ~300 token
新日记输入:     ~500 token
AI输出:         ~800 token (max_tokens限制)
─────────────────────────────
总计:          ~1600 token / 次
```

### 容错设计

```typescript
async function safeUpdateDraft(draft: InsightDraft, diary: string): Promise<InsightDraft> {
  try {
    const newDraft = await updateInsightDraft(draft, diary);
    // JSON合法性检查
    if (!isValidDraft(newDraft)) {
      console.error('草稿格式异常，保留旧版本');
      return draft;
    }
    return newDraft;
  } catch (e) {
    // AI调用失败：回声照常生成，用旧草稿
    console.error('草稿更新失败，使用旧版本:', e);
    return draft;
  }
}
```

**关键设计决策**：草稿更新失败不应该阻断回声生成。回声是用户体验，草稿是基础设施。基础设施挂了，用缓存顶上。

## 7. 最刺耳的一句话

**你们花了两周讨论洞察草稿的字段设计、存储方案、更新策略，但真正的问题是：你们还没有验证用户是否在意AI回声是否有记忆。**

**如果用户根本不看回声，或者看了也无所谓——你精心设计的整个持久化系统就是最精致的浪费。先用最蠢的方案（localStorage存一个JSON，每次都覆盖），看用户留存率有没有变化。如果有变化，再优化。如果没有，停掉整个功能。**

**工程师最大的幻觉：把"我能做"当成"我该做"。先证明回声的记忆能力对留存有因果影响，再来讨论该存哪些字段。**
