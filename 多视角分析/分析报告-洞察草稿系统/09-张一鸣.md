# 09 - 张一鸣视角：用推荐系统思维设计洞察草稿

> "信息分发的效率决定了产品的天花板。洞察草稿本质上是一个针对用户自我的信息推荐系统——只不过推荐的不是内容，而是用户尚未意识到的自己。"

---

## 一、核心类比：洞察草稿 = 用户画像 + 推荐引擎

推荐系统的本质是：**在用户没有明确表达需求时，把最相关的信息推到他面前。**

洞察草稿的本质是：**在用户没有意识到自己的模式时，把最真实的成长线索呈现给他。**

两者的底层结构完全一致：

| 推荐系统 | 洞察草稿系统 |
|---------|------------|
| 用户画像 (User Profile) | 心理画像 (Insight Profile) |
| 内容特征 (Item Feature) | 日记特征 (Entry Feature) |
| 行为信号 (Behavior Signal) | 反馈信号 (Feedback Signal) |
| 召回 + 排序 | 提取 + 置信度排序 |
| 冷启动 | 首次日记 |
| 探索与利用 | 新洞察 vs 稳定洞察 |

---

## 二、数据模型：InsightProfile（洞察画像）

### 2.1 用户画像不是一张表，是一个向量

推荐系统不把用户画像存在一张扁平的表里。它把用户表示为一个**高维向量**，每个维度代表一个潜在兴趣因子。

洞察草稿也一样。用户的"心理画像"不应该只有4个字段，而应该是一个**结构化的、可演化的向量空间**。

```typescript
// 核心数据结构：InsightProfile
interface InsightProfile {
  userId: string;
  version: number;                    // 版本号，每次增量更新 +1
  updatedAt: string;                  // 最后更新时间

  // 维度1：今日主线（短期上下文，衰减快）
  todayNarrative: {
    text: string;                     // 当前主线描述
    confidence: number;               // 置信度 0-1
    sources: string[];                // 支撑来源（日记条目ID列表）
    decayRate: number;                // 衰减速率，主线变化快
    lastReinforced: string;           // 最后被强化的时间
  };

  // 维度2：核心矛盾（中期模式，衰减慢）
  coreTensions: Array<{
    id: string;                       // 矛盾唯一ID
    pole1: string;                    // 矛盾的一极
    pole2: string;                    // 矛盾的另一极
    tension: string;                  // 矛盾描述
    strength: number;                 // 强度 0-1
    occurrences: string[];            // 出现的日记ID
    firstSeen: string;                // 首次发现时间
    lastSeen: string;                 // 最近一次出现时间
    stability: number;                // 稳定性（出现频率）
  }>;

  // 维度3：人格特质（长期特征，几乎不衰减）
  traits: Array<{
    name: string;                     // 特质名称
    score: number;                    // 0-1
    evidence: string[];               // 证据链
    confidence: number;               // 置信度
    trend: 'emerging' | 'stable' | 'fading';  // 趋势
  }>;

  // 维度4：成长方向（预测性维度）
  growthDirections: Array<{
    direction: string;                // 方向描述
    readiness: number;                // 成熟度 0-1
    signals: string[];                // 信号来源
    stage: 'seed' | 'sprout' | 'growing' | 'blooming';
  }>;

  // 元数据：用于调试和分析
  metadata: {
    totalEntries: number;             // 累计分析的日记数
    avgConfidence: number;            // 平均置信度
    lastFullAnalysis: string;         // 最后一次完整分析的时间
    updateHistory: Array<{            // 更新历史
      date: string;
      changes: string[];              // 本次变更摘要
    }>;
  };
}
```

### 2.2 关键设计决策：不同维度不同衰减率

推荐系统中，用户的短期兴趣（刚搜了"iPhone"）衰减快，长期兴趣（科技爱好者）衰减慢。

洞察草稿完全一样：

```
今日主线    →  衰减率 0.3/天   →  3天后基本失效，必须被新信息替代
核心矛盾    →  衰减率 0.02/天  →  能持续数周，除非反复出现新证据覆盖
人格特质    →  衰减率 0.001/天 →  几乎永久，除非大量反向证据
成长方向    →  衰减率 0.01/天  →  中等速度，需要持续信号维持
```

**这个衰减率的设计比存储结构本身更重要。** 衰减率决定了系统是"活的"还是"死的"。

## 三、增量更新：召回-排序-合并流水线

### 3.1 不要重新生成，要增量合并

推荐系统从来不会因为用户看了一条新视频就重建整个画像。它做的事情是：

1. **召回**：从新行为中提取候选特征
2. **排序**：按信号强度排序
3. **合并**：与现有画像做加权融合

洞察草稿的增量更新应该完全按照这个流水线：

```
新日记 → [特征提取] → [候选洞察] → [置信度排序] → [与现有画像合并] → [更新后画像]
```

### 3.2 增量更新 Prompt 设计

这是整个系统最关键的技术细节。Prompt 必须让 AI 做合并，而不是重新生成：

```typescript
// 增量更新的核心 Prompt 模板
const INCREMENTAL_UPDATE_PROMPT = `
你是一个心理画像分析师。你正在维护一份关于用户的长期心理画像。

## 当前画像（置信度加权）
${JSON.stringify(currentProfile, null, 2)}

## 用户最新日记
${newEntry.content}

## 用户对该画像的反馈历史
${JSON.stringify(feedbackHistory, null, 2)}

## 任务
根据新日记，对当前画像做**最小化增量更新**。规则：

1. **今日主线**：如果新日记的主题与当前主线一致，增强置信度；如果不一致，用新主线替换旧主线，但保留旧主线作为"近期副线"。

2. **核心矛盾**：
   - 如果新日记体现了已知矛盾，增加 strength（每次 +0.1，上限 1.0）
   - 如果新日记体现了一个新的对立模式，新增候选矛盾（初始 strength 0.3）
   - 如果新日记与某个已知矛盾矛盾（用户似乎解决了它），降低 strength

3. **人格特质**：
   - 已有特质：根据新证据调整 score（幅度 ±0.05，避免剧烈波动）
   - 新特质：仅当有明确证据时新增，初始 score 0.3，confidence 0.2
   - 低于 threshold（score < 0.15）的特质移入 fading 状态

4. **成长方向**：
   - 根据新信号调整 readiness
   - 新方向初始 stage 为 seed，需要至少3次独立信号才能进入 sprout

## 输出格式
返回一个 JSON，包含：
- updatedProfile: 更新后的完整画像
- changes: 本次变更列表（每条用一句话描述）
- newInsights: 本次新发现的洞察（如果有）
- strengthenedInsights: 本次被强化的已有洞察
- deprecatedInsights: 本次降级或移除的洞察

只输出 JSON，不要解释。`
```

### 3.3 置信度的贝叶斯更新

推荐系统用贝叶斯方法更新用户偏好。洞察草稿也应该：

```
新置信度 = 旧置信度 × (1 + 信号强度 × 相关性系数)
```

具体规则：

| 信号类型 | 置信度变化 | 说明 |
|---------|----------|------|
| 用户点赞了相关洞察 | +0.15 | 正反馈，强信号 |
| 用户无反馈 | -0.02 | 自然衰减 |
| 用户忽略（滑过） | -0.05 | 弱负信号 |
| 用户主动标记"不准" | -0.25 | 强负信号 |
| 新日记重复出现该模式 | +0.08 | 自然强化 |
| 多日未出现 | -0.01/天 | 时间衰减 |

## 四、存储策略：分层存储 + 向量索引

### 4.1 三层存储架构

```
┌─────────────────────────────────────────────┐
│              Layer 1: 热存储                 │
│         当前 InsightProfile JSON             │
│         IndexedDB / SQLite                   │
│         每次回声时读取，毫秒级                │
└─────────────────────────────────────────────┘
                    │
┌─────────────────────────────────────────────┐
│              Layer 2: 温存储                 │
│         历史版本快照 + 变更日志               │
│         用于回溯"我的洞察是怎么变化的"        │
│         保留最近 30 个版本                    │
└─────────────────────────────────────────────┘
                    │
┌─────────────────────────────────────────────┐
│              Layer 3: 冷存储                 │
│         原始日记 + 提取的特征向量              │
│         用于未来的深度分析和模型训练           │
└─────────────────────────────────────────────┘
```

### 4.2 数据库 Schema

```sql
-- 主表：当前画像
CREATE TABLE insight_profiles (
  user_id TEXT PRIMARY KEY,
  profile_json TEXT NOT NULL,
  version INTEGER DEFAULT 1,
  updated_at DATETIME DEFAULT CURRENT_TIMESTAMP,
  entry_count INTEGER DEFAULT 0,
  avg_confidence REAL DEFAULT 0
);

-- 版本历史：支持回溯
CREATE TABLE profile_versions (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  user_id TEXT NOT NULL,
  version INTEGER NOT NULL,
  profile_json TEXT NOT NULL,
  changes_json TEXT,           -- 本次变更摘要
  triggered_by_entry_id TEXT,  -- 触发更新的日记ID
  created_at DATETIME DEFAULT CURRENT_TIMESTAMP,
  FOREIGN KEY (user_id) REFERENCES insight_profiles(user_id)
);

-- 反馈表：用户对洞察的反馈
CREATE TABLE insight_feedbacks (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  user_id TEXT NOT NULL,
  insight_id TEXT NOT NULL,     -- 洞察的唯一标识
  insight_type TEXT NOT NULL,   -- tension/trait/direction/narrative
  feedback_type TEXT NOT NULL,  -- like/dislike/ignore/mark_inaccurate
  created_at DATETIME DEFAULT CURRENT_TIMESTAMP,
  FOREIGN KEY (user_id) REFERENCES insight_profiles(user_id)
);

-- 特征向量：用于相似度计算
CREATE TABLE entry_features (
  entry_id TEXT PRIMARY KEY,
  user_id TEXT NOT NULL,
  emotion_vector TEXT,         -- 情绪向量 JSON
  topic_vector TEXT,           -- 主题向量 JSON
  extracted_at DATETIME DEFAULT CURRENT_TIMESTAMP
);
```

### 4.3 前后端存储分工

```
前端 (IndexedDB):
  ├── insight_profile_cache     // 当前画像缓存，离线可用
  ├── feedback_queue            // 待同步的反馈队列
  └── pending_entries           // 待同步的日记队列

后端 (SQLite):
  ├── insight_profiles          // 权威画像
  ├── profile_versions          // 版本历史
  ├── insight_feedbacks         // 反馈数据
  └── entry_features            // 特征向量
```

## 五、冷启动策略：前5篇日记的特殊处理

推荐系统的冷启动是最难的问题。洞察草稿也一样——前几篇日记时，系统几乎没有数据，但恰恰是这个时候用户最需要被"看见"。

### 5.1 冷启动分阶段策略

```
第1篇日记：
  ├── 不做画像构建
  ├── 仅提取情绪关键词和主题
  ├── 回声正常生成（不含画像注入）
  └── 输出："我注意到你今天提到了[关键词]，我会慢慢了解你。"

第2-3篇日记：
  ├── 开始构建种子画像
  ├── 识别最明显的情绪模式（如：总是提到工作压力）
  ├── 置信度全部设为 0.2（低置信度，高探索性）
  └── 输出中加入"初步观察"标签

第4-5篇日记：
  ├── 画像开始稳定
  ├── 首次识别核心矛盾（如果有足够信号）
  ├── 置信度提升到 0.4
  └── 输出中开始出现"我越来越了解你了"

第6篇+日记：
  ├── 正常增量更新流程
  ├── 置信度按贝叶斯规则更新
  └── 画像开始真正有用
```

### 5.2 冷启动的"探索-利用"平衡

推荐系统在冷启动时会故意推荐一些多样性内容来探索用户偏好。洞察草稿也应该：

```typescript
// 探索系数：早期高，后期低
function getExplorationFactor(entryCount: number): number {
  if (entryCount <= 3) return 0.7;   // 70% 探索
  if (entryCount <= 10) return 0.4;  // 40% 探索
  if (entryCount <= 30) return 0.2;  // 20% 探索
  return 0.1;                        // 10% 探索（稳定期）
}

// 探索意味着：即使某个洞察置信度不高，也可以尝试呈现给用户
// 利用意味着：只呈现高置信度的洞察
```

## 六、反馈闭环：用户行为即训练信号

### 6.1 反馈信号的采集

推荐系统的命脉是用户行为数据。洞察草稿的命脉是用户对洞察的反馈。

```typescript
// 反馈信号类型
enum FeedbackSignal {
  // 显式反馈
  RESONATE = 'resonate',           // 用户点了"说到我心里了"
  NOT_QUITE = 'not_quite',        // 用户点了"不太准"
  REVELATION = 'revelation',      // 用户点了"我自己都没注意到"

  // 隐式反馈
  DWELL_LONG = 'dwell_long',      // 在洞察区域停留 > 5秒
  DWELL_SHORT = 'dwell_short',    // 快速滑过
  SHARE = 'share',                // 分享了这个洞察
  COPY = 'copy',                  // 复制了这个洞察文本
  EXPAND = 'expand',              // 点击展开详情
}
```

### 6.2 反馈对画像的影响权重

```typescript
const FEEDBACK_WEIGHTS: Record<FeedbackSignal, number> = {
  [FeedbackSignal.REVELATION]: 0.25,   // 最强正信号
  [FeedbackSignal.RESONATE]: 0.15,
  [FeedbackSignal.SHARE]: 0.20,
  [FeedbackSignal.COPY]: 0.15,
  [FeedbackSignal.EXPAND]: 0.08,
  [FeedbackSignal.DWELL_LONG]: 0.05,
  [FeedbackSignal.DWELL_SHORT]: -0.05,
  [FeedbackSignal.NOT_QUITE]: -0.20,   // 强负信号
};
```

### 6.3 负反馈的特殊处理

**这一点极其重要。** 推荐系统如果忽视负反馈，用户会觉得"算法不懂我"然后流失。洞察草稿如果忽视"不准"的反馈，用户会觉得"AI在胡说"然后关掉。

```typescript
function handleNegativeFeedback(
  profile: InsightProfile,
  insightId: string,
  feedbackType: 'not_quite' | 'mark_inaccurate'
): InsightProfile {
  const insight = findInsight(profile, insightId);
  if (!insight) return profile;

  if (feedbackType === 'mark_inaccurate') {
    // 用户明确标记"不准"：大幅降低置信度
    insight.confidence -= 0.25;

    // 如果连续两次被标记不准，进入"冷却期"
    if (insight.confidence < 0.2) {
      insight.status = 'cooldown';
      insight.cooldownUntil = addDays(new Date(), 7);
      // 7天内不再展示该洞察
    }
  }

  return profile;
}
```

## 七、注入策略：把画像变成回声的"上下文"

### 7.1 上下文窗口的优先级排序

回声生成时，上下文窗口是有限的。需要决定哪些画像信息优先注入：

```
优先级排序：
1. 今日主线（必须注入，与当前日记直接相关）
2. 与当前日记最相关的 1-2 个核心矛盾（相关性匹配）
3. 置信度最高的 2-3 个人格特质（稳定性高，风险低）
4. 最成熟的 1 个成长方向（如果有）
5. 最近的反馈摘要（让用户感觉被"记住"了）
```

### 7.2 注入的 Prompt 模板

```typescript
const ECHO_WITH_PROFILE_PROMPT = `
你是小象，一个温柔的成长陪伴者。你正在回应用户今天的日记。

## 你对这个人的了解（置信度 ${profile.avgConfidence}）
${formatProfileForEcho(profile)}

## 今天的日记
${newEntry.content}

## 用户最近对你洞察的反馈
${formatRecentFeedback(recentFeedbacks)}

## 回应要求
1. 先回应今天日记的情绪，共情优先
2. 如果今天的日记与你已知的某个模式相关，自然地提一句
   - 用"我注意到..."而不是"我发现你总是..."
   - 置信度低于 0.4 的洞察不要主动提，除非用户问
3. 如果用户之前标记过某个洞察"不准"，绝对不要重复那个洞察
4. 保持温暖、不说教、不评判

请用 3-5 句话回应。`;
```

### 7.3 注入的安全边界

```typescript
function shouldInjectInsight(
  insight: Insight,
  currentEntry: Entry,
  recentFeedbacks: Feedback[]
): boolean {
  // 安全规则1：置信度过低不注入
  if (insight.confidence < 0.3) return false;

  // 安全规则2：冷却期内不注入
  if (insight.status === 'cooldown') return false;

  // 安全规则3：被标记不准的洞察不注入
  if (recentFeedbacks.some(f =>
    f.insightId === insight.id &&
    f.type === 'mark_inaccurate'
  )) return false;

  // 安全规则4：与当前日记无关的洞察不注入
  const relevance = computeRelevance(insight, currentEntry);
  if (relevance < 0.3) return false;

  return true;
}
```

## 九、"越用越精准"的量化指标

推荐系统用 A/B 测试衡量效果。洞察草稿也需要可量化的精准度指标：

```typescript
// 精准度指标
interface PrecisionMetrics {
  // 1. 反馈正向率
  positiveRate: number;  // resonates / total_feedbacks

  // 2. 洞察留存率
  insightRetention: number;  // 存活超过7天的洞察 / 总洞察数

  // 3. 画像稳定性
  profileStability: number;  // 1 - (版本间变更幅度 / 总维度数)

  // 4. "恍然大悟"率
  revelationRate: number;  // "我自己都没注意到"反馈 / 总反馈

  // 5. 冷却率（越低越好）
  cooldownRate: number;  // 进入冷却的洞察 / 总洞察
}
```

**目标曲线：**

```
精准度
  ↑
  │                    ___________
  │                ___/
  │            ___/
  │        ___/
  │    ___/
  │___/
  └──────────────────────────────────→ 使用天数
   1   5   10   20   30   50   100

前5天：快速上升（冷启动阶段，每篇日记都带来大量新信息）
5-20天：稳步上升（模式开始显现，矛盾开始浮现）
20天后：趋于平稳（画像稳定，偶尔有新发现）
```

## 十、最刺耳的一句话

> **你们把洞察草稿当成一个"生成任务"来做，但推荐系统的历史已经证明：没有任何一个"生成一次就扔掉"的系统能产生真正的用户价值。今日头条不做"为你生成今日推荐然后丢弃"，它做的是"持续积累对你的理解直到你离不开它"。你们现在做的事情，相当于每次用户打开今日头条都把他当新用户——这不是技术问题，是产品哲学的缺陷。洞察草稿系统如果不能像推荐引擎一样积累、衰减、反馈、迭代，它就只是一个高级版的随机语录生成器，用户用三次就会发现"它根本不认识我"，然后永远离开。**
