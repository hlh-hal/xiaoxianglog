# 深一层追问设计：资源与优先级视角

> 作者视角：任正非（华为创始人，资源配置与战略落地思维）

---

## 核心判断

深一层追问，不是技术问题，是**资源配置问题**。团队精力有限，AI调用有成本，用户耐心有天花板。打仗的原则只有一条：**集中兵力，先打一个点，打穿打透，再铺开。**

不要设计五层，不要设计完美。先问自己一个问题：**如果只有两周时间和一个工程师，你做什么能让用户明天就想点"深一层"？**

---

## 一、资源现实：你有什么，缺什么

### 1.1 你手里有的资源

| 资源 | 状态 | 备注 |
|------|------|------|
| DailyEchoCard组件 | 存在，可改造 | 不需要从零开始 |
| /chat/complete 接口 | 存在 | 可以复用，不需要新接口 |
| AI模型能力 | 能生成回声 | 但不保证追问质量 |
| 用户数据（历史日记） | 有，但不完整 | 个性化是后期的事 |

### 1.2 你缺的资源

| 缺失项 | 严重程度 | 应对策略 |
|---------|----------|----------|
| 追问质量评估体系 | 高 | 先用人工抽检，不上自动化 |
| 用户对"深一层"的认知 | 高 | 用引导语解决，不靠功能复杂度 |
| 多层数据结构 | 中 | 简单改，不要过度设计 |
| 后端新接口 | 低 | 复用现有接口，加参数即可 |

**核心原则：不要因为缺资源就等。先用现有资源把最小版本跑起来，用真实数据告诉你该往哪里投入。**

---

## 二、先做什么，后做什么：三阶段打法

### 第一阶段：验证需求（1周）

**目标：确认用户真的想点"深一层"，而不是我们自己想象的。**

只做三件事：

1. **把"换一句"改成"深一层"按钮**——UI层面的替换，一天完工
2. **点击后生成一层追问，覆盖原回声**——复用现有接口，传入上一层内容作为上下文
3. **加一行引导语**——"想再往里看看吗？"

不做：
- 不做多层叠放UI
- 不做层级指示器
- 不做数据结构改造
- 不做新接口

**验收标准：按钮点击率 > 30%。如果低于30%，停手，回去重新想这个功能有没有必要做。**

这不是偷懒，这是**侦察**。你不知道敌人在哪，不要把整个集团军拉上去。先派一个连，摸清地形。

### 第二阶段：打穿核心体验（2周）

**目标：让"深一层"从能用变成好用，用户愿意连续追问2-3次。**

只做四件事：

1. **实现2-3层追问链**——不是5层，是3层。3层够了。
2. **改造数据结构**——给DailyEcho加一个layers数组，存每层内容
3. **写好Prompt**——这是这个功能的命脉，投入60%的精力在Prompt上
4. **加一个安全阀**——检测到用户情绪过重时，自动停止追问，温和收束

不做：
- 不做L4、L5（太深了，现阶段没有意义）
- 不做个性化（没有足够数据）
- 不做视觉递进效果（背景色渐变之类）
- 不做"保存为觉察"

**验收标准：平均追问深度 ≥ 2层。L2点击率 ≥ 50%（基于L1已点击用户）。**

### 第三阶段：加固与扩展（2-4周）

**此时你已经有了真实数据，知道用户在哪一层流失最多，知道Prompt哪里有问题。**

根据数据决定做什么：

- 如果L2流失率高 → 优化Prompt，不急着加L3
- 如果用户反复点击但觉得不够深 → 加L3-L4
- 如果用户想保存追问结果 → 加"保存洞察"
- 如果某些日记不适合追问 → 加适用性判断

**不要提前做第三阶段的事。数据会告诉你答案。**

## 三、最小可行版本（MVP）的边界

### MVP必须有的（没有就不上线）

| 功能 | 原因 | 工时估算 |
|------|------|----------|
| "深一层"按钮替换"换一句" | 入口，没有就没有功能 | 2小时 |
| 点击后AI生成追问回声 | 核心价值，必须有 | 1天（含Prompt调试） |
| 追问基于上一层内容 | "深"的前提是"基于前面" | 含在上一条中 |
| 最多追问3次的硬限制 | 防止无限追问烧钱 | 2小时 |
| 追问过程中的loading状态 | 用户需要知道系统在工作 | 2小时 |
| 到达上限时的温和收束 | 不能让用户体验突然断裂 | 1小时 |

### MVP可以没有的（有了是锦上添花）

| 功能 | 为什么可以没有 | 什么时候加 |
|------|----------------|------------|
| 多层叠放展示 | 3层以内，覆盖即可 | 第三阶段 |
| 层级指示器 | 用户数得过来 | 超过3层时 |
| 视觉递进效果 | 体验加分项，非核心 | 第三阶段 |
| 新接口/后端改造 | 复用现有接口够用 | 性能瓶颈时 |
| 历史日记数据接入 | 个性化是奢侈品 | 用户量起来后 |
| "保存为觉察" | 功能延伸，不是核心 | 数据验证后 |

## 四、Prompt：花80%的精力在这里

### 为什么Prompt是命脉

技术层面，深一层就是一个API调用，没有任何新东西。**决定这个功能生死的，是AI说出来的话有没有价值。**

一句话的追问如果让用户觉得"被看见了"，他会继续点。如果让他觉得"AI在说废话"，他再也不会点第二次。没有第二次，这个功能就是废的。

### Prompt投入分配

```
总精力分配：

Prompt设计与调试        ████████████████░░░░  80%
前端交互实现            ███░░░░░░░░░░░░░░░░░  15%
数据结构/API            █░░░░░░░░░░░░░░░░░░░   5%
```

### 追问Prompt的核心要求

1. **基于用户日记的具体细节**——不能泛泛而谈，必须引用用户写到的某个词、某句话
2. **只问一个问题**——不要"你怎么看？也许你可以想想……"这种散弹式追问
3. **比上一层更深，但不跨太远**——L1到L2是从事实到情绪，不是从事实到哲学
4. **语气是好奇的，不是分析的**——"我注意到……"而不是"你的行为模式表明……"
5. **不超过80个字**——长了用户不看

### 安全阀Prompt

```
在生成追问前，先检查：
- 用户日记是否包含自伤/自杀倾向 → 是：不追问，温和提示
- 用户日记是否过于简短（<20字） → 是：不追问，正常回声即可
- 当前情绪强度是否过高 → 是：降低追问深度，温和收束
```

## 五、资源投入的优先级排序

用一个标准判断所有取舍：**这件事能不能让用户明天就想再点一次"深一层"？**

| 优先级 | 事项 | 能否让用户再点一次？ | 投入 |
|--------|------|---------------------|------|
| P0 | Prompt质量（追问有没有价值） | 能，直接决定 | 大量 |
| P0 | 点击后的响应速度（<3秒） | 能，慢了就走了 | 优化 |
| P1 | 到达上限的收束体验 | 间接能，不能太突兀 | 小量 |
| P1 | 3层硬限制 | 间接能，防烧钱 | 小量 |
| P2 | 多层UI叠放 | 不能，用户不在乎形式 | 后期 |
| P2 | 层级指示器 | 不能，3层以内不需要 | 后期 |
| P3 | 视觉递进效果 | 不能，锦上添花 | 后期 |
| P3 | 个性化深度 | 不能，数据不够 | 更后期 |

## 六、风险与底线

### 必须守住的三条底线

1. **不能让用户觉得自己被"分析"了**——这是日记应用，不是心理咨询。一旦用户觉得在被评判，信任就没了，产品就没了。
2. **不能烧钱**——AI调用有成本。3层追问 = 3次API调用。如果日活1万，每人每天追问2次 = 6万次调用。这个成本必须提前算清楚。
3. **不能碰心理治疗的边界**——追问到情绪层就够了，不要试图帮用户做认知重构。那是咨询师的工作，不是产品的工作。

### 不需要担心的事

- **UI不够精美**——用户在乎的是AI说的话有没有价值，不是背景色渐变
- **功能不够复杂**——3层比5层好。简单的功能用户才敢用
- **没有个性化**——现阶段个性化是伪需求，你没有足够的数据做真正的个性化

## 七、与"继续聊聊"的关系：不做选择题

"深一层"和"继续聊聊"不是二选一，是两条路：

- **深一层**：AI引导，纵向深挖，有终点，3层封顶
- **继续聊聊**：用户主导，横向展开，无终点

**MVP阶段只做"深一层"，不做"继续聊聊"的改造。** 两个功能独立存在，不互斥。用户在"深一层"结束后，自然可以点"继续聊聊"。不需要做复杂的衔接逻辑。

等到"深一层"跑通了，数据积累够了，再考虑两者如何联动。

---

## 八、一句话总结执行策略

```
第一周：把按钮换了，Prompt写好，上线，看数据。
第二三周：根据数据调优Prompt，加到3层，加安全阀。
第四周起：数据决定一切。不做假设，只做验证。
```

不要设计五层。不要设计完美。不要设计惊喜。**先把最简单的事情做好，让用户愿意点第二次，你就赢了。**

---

## 最刺耳的一句话

**你们花了大量时间讨论五层追问、信息增益算法、视觉递进效果、个性化权重——这些都很好，但都是打完仗以后的勋章。现在仗还没打，你连用户愿不愿意点这个按钮都不知道。一个工程师、一周时间、一个Prompt，这就是你验证这件事需要的全部资源。你不是资源不够，你是把资源花在了想上面，而不是做上面。想一百遍不如做一遍，做出来被用户骂一句，比想一百年都值钱。最怕的不是做错，是想了三个月还没动手。**
